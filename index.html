HubSynk Wiki

Complete documentation — architecture, cryptographic model, security, and developer reference.

Visão Geral

O HubSynk é um hub de produtividade open source para Windows que centraliza, organiza e lança ferramentas (.exe, .py, GitHub) num único lugar com interface Fluent Design. Ele também possui um sistema próprio de distribuição segura de ferramentas via pacotes .hubsynk assinados digitalmente.

📦
Gerenciamento de Ferramentas
Instala, organiza e remove ferramentas oficiais, customizadas e scripts Python.
🔐
Segurança Criptográfica
Pacotes .hubsynk assinados com RSA 4096 + hash SHA-256 do executável.
🐙
Integração GitHub
Baixa e executa ferramentas diretamente de repositórios e subpastas do GitHub.
⭐
Favoritos & Busca
Marque ferramentas como favoritas e filtre por nome ou descrição em tempo real.

hubsynk.py — Ponto de Entrada

Arquivo mínimo que instancia os componentes principais e inicia o loop Tkinter. É o único arquivo que precisa ser executado.

def main():
    root = tk.Tk()

    config_manager  = DevtoolConfig()       # gerencia JSON de configuração
    tool_processor  = ToolProcessor(config_manager)  # instala + verifica
    tool_launcher   = ToolLauncher()        # executa as ferramentas

    app = DevtoolApp(root, config_manager, tool_processor, tool_launcher)
    root.mainloop()hubsynk.py

O padrão aqui é injeção de dependência: cada componente recebe o que precisa pelo construtor, sem importações cruzadas ou singletons globais.

constants.py — Configurações Globais

Centraliza todas as constantes usadas pela aplicação. Funciona como o único lugar onde você precisa editar para alterar comportamentos globais.

🔑
Por que a chave pública fica hardcoded aqui? A chave pública pode ser conhecida por qualquer pessoa — ela só verifica assinaturas, nunca cria. Ao hardcodá-la no executável final, você garante que o Devtool sempre vai verificar pacotes contra a sua chave, sem depender de um arquivo externo que poderia ser substituído.

tool_processor.py — Instalação e Verificação v2.0

O coração da segurança do Devtool. A classe ToolProcessor processa todos os tipos de ferramenta, com verificação criptográfica completa para pacotes oficiais.

Fluxo de instalação de ferramenta oficial

1
Extrair o .hubsynk

O ZIP é extraído em uma pasta temporária com nome UUID dentro de TOOLS_DIR.

2
Ler e validar tool_config.json

Verifica existência e campos obrigatórios: name, exe_file, version, description.

3
Verificar assinatura RSA

O conteúdo bruto do JSON é verificado contra signature.sig usando a chave pública de constants.py. Falha → abortado.

4
Verificar hash SHA-256 do .exe

(novo v2.0) Recalcula o SHA-256 do executável extraído e compara com exe_sha256 do JSON assinado. Falha → abortado.

5
Registrar no config

Adiciona metadados ao hub_config.json via config_manager.add_tool().

Tipos de ferramenta suportados

MétodoTipoVerificação criptográfica
process_official_tool()Pacote .hubsynk✅ RSA + SHA-256
process_custom_tool()Executável .exe qualquer❌ (ferramenta do usuário)
process_python_tool()Script .py❌ (ferramenta do usuário)

tool_launcher.py — Execução

A classe ToolLauncher executa ferramentas de qualquer tipo. É inteligente o suficiente para detectar o tipo e tratar erros específicos.

Lógica de execução

# .exe → subprocess.Popen direto
subprocess.Popen([exe_path], cwd=os.path.dirname(exe_path))

# .py → python com captura de erro nos primeiros 1s
process = subprocess.Popen([sys.executable, exe_path], stderr=PIPE, ...)
process.communicate(timeout=1)   # se travar, o script está rodando normalmente

# pasta (GitHub) → _find_runnable() detecta o arquivo principaltool_launcher.py

Detecção de arquivo principal em pastas

Para ferramentas baixadas do GitHub (que são pastas), o launcher procura na seguinte ordem de prioridade:

  1. main.py, app.py, run.py, index.py, gui.py
  2. Qualquer .py com nome igual ao da pasta
  3. Qualquer .py que não seja setup.py ou __init__.py
🐍
Erro Python 3.13 — audioop removido Se um script Python falhar com ModuleNotFoundError: No module named 'audioop', o launcher detecta e exibe uma mensagem específica orientando o usuário a instalar audioop-lts.

github_manager.py — Integração GitHub

A classe GitHubManager permite baixar repositórios ou subpastas do GitHub diretamente pela interface.

URLs suportadas

Formato de URLResultado
https://github.com/user/repoBaixa o repositório inteiro
https://github.com/user/repo/tree/main/pastaBaixa só a subpasta especificada

Como funciona internamente

  1. Faz parse da URL para extrair owner, repo, branch e subfolder
  2. Baixa o ZIP do repositório via https://github.com/owner/repo/archive/refs/heads/branch.zip
  3. Se main falhar, tenta master automaticamente
  4. Extrai somente os arquivos dentro do prefixo desejado
  5. Salva em APP_DATA_PATH/github_tools/nome_da_pasta/

utils.py — Utilitários

Contém dois componentes independentes:

calculate_file_hash()

Calcula o hash SHA-256 de qualquer arquivo em blocos de 4KB. Usado internamente para evitar carregar arquivos grandes na memória de uma vez.

IconCache

Cache LRU de ícones de ferramentas. Usa @lru_cache do Python para evitar recarregar a mesma imagem do disco repetidamente. Suporta tamanho máximo configurável (padrão: 100 ícones).

Interface gráfica (GUI) para desenvolvedores criarem, assinarem e empacotarem ferramentas no formato .hubsynk. Fica na pasta devtools/ e é separado do Devtool principal.

Aba 1 — Security Keys

Gera um novo par de chaves RSA 4096-bit e salva em private_key.pem e public_key.pem na pasta devtools/. Use depois de gerar para atualizar PUBLIC_KEY em constants.py.

signer_logic.py — Lógica de Assinatura v2.0

Contém as duas funções principais dos DevTools.

generate_keys()

Gera um par RSA 4096-bit. Retorna os bytes PEM da chave privada (PKCS8, sem criptografia) e da chave pública (SubjectPublicKeyInfo).

sign_and_package_tool()

def sign_and_package_tool(exe_path, private_key_path, name, version, description):
    # 1. Calcula SHA-256 do .exe
    exe_hash = _sha256_file(exe_path)

    # 2. Monta tool_config.json com o hash incluído
    tool_config_data = {
        "name": name,
        "exe_file": os.path.basename(exe_path),
        "exe_sha256": exe_hash,   # ← garante integridade do binário
        "version": version,
        "description": description,
        "signature_file": "signature.sig"
    }

    # Serialização canônica: sort_keys=True garante mesmo resultado em qualquer OS
    config_bytes = json.dumps(tool_config_data, indent=4, sort_keys=True).encode("utf-8")

    # 3. Assina o JSON com RSA-PSS + SHA-256
    signature = private_key.sign(
        config_bytes,
        padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
        hashes.SHA256()
    )

    # 4. Empacota em .hubsynk (ZIP)
    with zipfile.ZipFile(output_zip, "w", zipfile.ZIP_DEFLATED) as zf:
        zf.write(exe_path, main_exe_name)
        zf.writestr("tool_config.json", config_bytes)
        zf.writestr("signature.sig", signature)signer_logic.py

Sistema Criptográfico

Algoritmo e parâmetros

ComponenteValorMotivo
Algoritmo de assinaturaRSA-PSSMais seguro que PKCS#1 v1.5; resistente a ataques de falsificação
Tamanho da chave4096 bitsMargem de segurança longa (padrão até ~2040+)
Hash da assinaturaSHA-256Padrão seguro e amplamente validado
MGF (Mask Generation Function)MGF1 + SHA-256Recomendado pelo padrão PSS
Salt lengthMAX_LENGTHMáxima aleatoriedade por assinatura
Hash do executávelSHA-256Detecta qualquer modificação no binário

O que cada chave pode e não pode fazer

AçãoChave PrivadaChave Pública
Criar assinatura válida✅❌
Verificar uma assinatura✅✅
Ser derivada da outraPública ← simPrivada ← impossível
Pode ser pública/compartilhada❌ Nunca✅ Sim
✅
A chave pública em constants.py é segura Expor a chave pública é o comportamento correto e esperado de um sistema de assinatura digital. Ela só verifica — nunca cria. Sem a private_key.pem, ninguém consegue forjar um pacote válido.

Formato .hubsynk

Um arquivo .hubsynk é um ZIP renomeado com conteúdo padronizado. Pode ser aberto por qualquer gerenciador de ZIP.

Conteúdo interno

minha_ferramenta.hubsynk (ZIP)
├── minha_ferramenta.exe ← o executável
├── tool_config.json ← metadados + hash do exe
├── signature.sig ← assinatura RSA binária
└── icon.ico ← (opcional) ícone da ferramenta

Estrutura do tool_config.json (v2.0)

{
    "description":  "Descrição da ferramenta",
    "exe_file":     "minha_ferramenta.exe",
    "exe_sha256":   "a3f8c2...hash SHA-256 do exe...",
    "icon_file":    "icon.ico",
    "name":         "Minha Ferramenta",
    "signature_file": "signature.sig",
    "version":      "1.0.0"
}tool_config.json
📌
Por que sort_keys=True na serialização? JSON não garante ordem das chaves. Ao usar sort_keys=True, o mesmo dicionário sempre gera os mesmos bytes em qualquer Python/OS, tornando a assinatura reproduzível e verificável de forma confiável.

Trocar o Par de Chaves

Necessário se a chave privada for comprometida ou se você quiser iniciar um novo ciclo de confiança.

Passo a passo

1
Gerar novas chaves

Abra devtools/hubsign.py → aba "Security Keys" → "Generate New Key Pair". Salva automaticamente private_key.pem e public_key.pem.

2
Atualizar constants.py

Abra public_key.pem, copie o conteúdo e substitua o valor de PUBLIC_KEY em src/constants.py.

3
Reasinar todos os pacotes

Pacotes assinados com a chave antiga vão falhar na verificação. Use o Devtool para reasinar cada .hubsynk com a nova chave privada.

4
Distribuir o Devtool atualizado

Compile e distribua o executável com o constants.py novo. Usuários com a versão antiga não conseguirão verificar os novos pacotes.

🚨
Nunca suba private_key.pem para o GitHub! Adicione ao .gitignore: devtools/private_key.pem. Se já foi commitada, a chave está comprometida e você deve gerar um novo par imediatamente.

Using Your Own Keys

The repository ships with the official developer keys. If you want to create your own ecosystem of signed tools, follow these steps.

⚠️
private_key.pem is not included in the repository For security reasons, the private key is never distributed publicly. It lives only on the developer's machine. If you cloned the repo and want to sign your own tools, follow the steps below.

Step 1 — Generate a new key pair

cd devtool
python hubsign.pybash

Go to the "Security Keys" tab → "Generate New Key Pair". Two files will be created:

FilePurposeSafe to share?
private_key.pemSign packages❌ Never — keep only on your machine
public_key.pemVerify signatures✅ Yes — can be made public

Step 2 — Update constants.py

PUBLIC_KEY = """-----BEGIN PUBLIC KEY-----
PASTE_YOUR_NEW_public_key.pem_CONTENT_HERE
-----END PUBLIC KEY-----"""src/constants.py

Step 3 — Recompile

pyinstaller build/hubsynk.specbash
🚨
If private_key.pem leaks Anyone with it can forge official packages. Generate a new pair immediately, update constants.py, recompile, and re-sign all existing packages.

FAQ

Posso distribuir ferramentas sem assinar?

Sim — como ferramentas "Custom" (não oficiais). O usuário seleciona diretamente o .exe via "Add Custom Tool". Não passa por verificação criptográfica e não aparece como "Official" na interface.

O que acontece se a biblioteca cryptography não estiver instalada?

O tool_processor.py detecta a ausência via CRYPTOGRAPHY_AVAILABLE = False e exibe um aviso, mas permite a instalação mesmo assim (degradação graciosa). Para produção, cryptography deve estar sempre presente.

Posso ter múltiplas chaves (para múltiplos desenvolvedores)?

Na arquitetura atual, o constants.py suporta apenas uma chave pública. Para múltiplos desenvolvedores, seria necessário alterar _verify_signature para iterar sobre uma lista de chaves públicas autorizadas.

O .hubsynk pode conter múltiplos arquivos além do .exe?

Sim — o ZIP pode ter qualquer quantidade de arquivos de suporte. Apenas o exe_file referenciado no tool_config.json precisa ter seu hash protegido. Arquivos adicionais não são verificados individualmente.

Posso rodar o HubSynk no Linux/macOS?

O código é multiplataforma em sua maior parte. O caminho de dados é detectado pelo OS (LOCALAPPDATA no Windows, ~/.hubsynk no Unix). A execução de .exe não funciona no Linux/macOS nativamente, mas scripts .py e ferramentas do GitHub funcionam normalmente.
